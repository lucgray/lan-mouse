## 结论与 90 分标准

目前不能认定达到 90 分：存在丢失按键释放、返回路径不恢复、图片单向失效等核心问题。下面是审查清单，不是已完成修复清单。没有实际 CPU、延迟、跨平台长时间测试，因此不编造当前综合分。

建议采用以下验收评分；未验证项不计“通过”。90 分还必须满足所有 P1 问题关闭，不能用界面优化抵消失控风险。

| 维度 | 权重 | 通过依据 |
|---|---:|---|
| 输入与返回正确性 | 35 | 队列拥塞、断续恢复、双向切换均不丢释放事件；1000 次往返无失控 |
| 延迟与资源 | 25 | 固定硬件下记录基线；局域网输入端到端 p95 ≤20ms、p99 ≤50ms；8 小时 RSS 无持续增长；静态剪贴板不反复编码 |
| 剪贴板体验 | 20 | 文本/图片两个连接方向、断线后同步、失败提示及最新内容顺序测试通过 |
| 故障反馈与恢复 | 15 | 界面正确区分待连接、已发送、已应用和失败；不需要用户靠重启恢复 |
| 配置可靠性 | 5 | 写入失败不破坏配置，监听能恢复，用户能收到保存失败提示 |

这些数值是提议的验收目标，不是已测性能。测试时需记录鼠标回报率、网络 RTT/丢包、显示刷新率、CPU 和系统版本。

## 第一轮：输入正确性与失控恢复

### R01 / P1：watchdog 删除返回边缘，输入恢复时不重建

- [ ] 修复并验证。
- 证据：`src/emulation.rs:273` 超时发出 Disconnected；`src/service.rs:652` 删除 incoming capture；后续 Input 在 `src/emulation.rs:486` 自动重建 emulation handle，却不发 Entered。
- 影响：输入恢复但无法通过原连接返回。已有现场日志支持，详见 `timeout-return-barrier-issue.md`。
- 建议：区分按键清理与会话销毁，保证恢复时输入状态和返回边缘一致。
- 验收：虚拟时间触发 watchdog，保留 DTLS，恢复普通 Input/Ping 而不发 Enter，仍可返回；真正断开也能完整清理。

### R02 / P1：Windows 队列满时丢弃键盘/鼠标按钮事件

- [ ] 修复并验证。
- 证据：`input-capture/src/windows.rs:59` 通道容量 10；`input-capture/src/windows/event_thread.rs:486,549` 对按钮和键盘调用 try_send，失败仅写日志，键盘事件仍被 hook 吞掉。
- 影响：队列满时 key-up/button-up 丢失，远端可能持续认为键或按钮按下；与普通 motion 的合并处理不同。源码已确认，尚未在 Windows 注入拥塞复现。
- 建议：motion 合并，离散事件使用保序的可靠缓冲/故障释放策略；不能简单改成 hook 内无限阻塞。
- 验收：高回报率移动同时按住/释放 Ctrl、Win、拖拽，故意暂停消费者，恢复后所有 pressed 状态为零且按钮顺序正确。

### R03 / P1：输入发送失败仍返回 Ok

- [ ] 修复并验证。
- 证据：`src/connect.rs:170–178` send 出错后 disconnect，但最后仍 Ok；`src/capture.rs:576` 依赖 Err 执行即时释放。
- 影响：本次失败不能触发预期的释放分支；后续事件可能才发现断连，停止移动时尤其不易恢复。
- 建议：返回原始/明确的发送错误，并验证释放操作幂等。
- 验收：假 transport 首次 send 失败且不再产生输入，捕获仍能及时释放，客户端状态与 UI 一致。

### R04 / P2：evdev 丢弃每次运动的小数余量

- [ ] 修复并验证。
- 证据：`input-emulation/src/evdev.rs:45` 每次 dx/dy 独立 round；`input-emulation/src/lib.rs:145` 支持小数灵敏度。
- 影响：例如连续 100 个 dx=0.4 全部变成 0，而非累计移动 40；低速移动有死区，灵敏度不线性。这里是确定的算术行为，实际体感未测。
- 建议：按输入来源保留余量，释放/销毁时明确重置。
- 验收：正负小数运动累计误差小于 1 单位，多来源不串状态。

## 第二轮：剪贴板协议与用户反馈

### R05 / P1：connect 侧接收循环漏掉 ClipboardImage

- [ ] 修复并验证。
- 证据：`src/connect.rs:353` 仅 ClipboardText 走变长解码；图片走固定长度解码，`lan-mouse-proto/src/lib.rs:232` 明确返回 BufferTooSmall。listen 侧已经使用 is_clipboard_event_type。
- 影响：图片经已有连接返回连接发起端时被丢弃，debug 关闭时用户看不到原因；不是所有方向都失败。
- 建议：统一两个方向的事件分类与解码。
- 验收：在同一个已建立连接上分别双向发送文本与小于 64KiB 的 PNG，四种组合均能应用；包含截断报文测试。

### R06 / P1：listen 将不完整剪贴板报文当字节流继续拼接

- [ ] 修复并验证。
- 证据：`src/listen.rs:380–397` 按声明长度循环 recv，无期限，未验证后续报文类型；当前发送端一次 send 一个编码后的事件。
- 影响：收到长度不匹配的剪贴板 datagram 后，后续 Ping/Input 可被当作剪贴板正文消耗，阻断事件解析。触发需要异常报文；没有证据证明本次现场故障由它触发。
- 建议：按 DTLS 应用消息边界拒绝截断帧；若需要应用层分块，应显式定义消息 ID、分块及超时。
- 验收：注入声明长度大于实际长度的报文，紧随 Ping、运动事件，后两者仍能正常处理。

### R07 / P2：剪贴板未连接/发送失败却报告成功，也没有重连补发

- [ ] 修复并验证。
- 证据：`src/connect.rs:222–239` 失败和未连接均可返回 Ok；`src/service.rs:538–565` 据此设置 shared。monitor 已记录 last_content，内容不变不会重新发事件，未见连接建立时重发缓存的调用。
- 影响：显示 shared 但对端拿不到；“连接后会同步”的日志承诺缺乏实现。
- 建议：区分 Sent/Queued/NotConnected/Failed；若支持补发，只保留最新内容并在连接就绪时发送。
- 验收：断线复制 A，再复制 B，重连只同步 B；失败不显示成功。

### R08 / P2：接收剪贴板两条路径的完成语义不同

- [ ] 修复并验证。
- 证据：`src/service.rs:441` await set 后通知；但 `src/service.rs:486` 先通知，再 spawn set。后一路多个 set 任务没有保证按接收顺序获取线程锁。
- 影响：写入失败仍显示 received；快速更新可能由较旧任务最后覆盖较新内容。线程 Mutex 保证互斥，不保证接收顺序。
- 建议：统一成有序、可合并最新值的写入 worker，写入成功后发完成通知。
- 验收：人为延迟 A 的写入、随后接收 B，最终值为 B；写入失败展示失败且不会冒充应用成功。

## 第三轮：性能、阻塞与资源

### R09 / P2：静态图片每 500ms 重新读取并 PNG 编码

- [ ] 优化并测量。
- 证据：`input-capture/src/clipboard.rs:70–113` 先 read_clipboard_content（包含 PNG 编码），之后才比较内容。每次还新建 Clipboard 实例。
- 影响：剪贴板无变化也重复 CPU/内存工作；大截图在超过传输上限之前已经编码完成。代码路径确定，成本尚未测量。
- 建议：优先平台变更通知/序列号；否则先比较原始内容或摘要再编码，限制尺寸/工作量，复用访问对象。
- 验收：静态 4K 截图保持 60 秒，变化后只编码一次；比较开启/关闭共享时 CPU、分配量及输入 p99。

### R10 / P1：持有同步锁时向有界剪贴板队列 blocking_send

- [ ] 修复并验证。
- 证据：`input-capture/src/clipboard.rs:108–135` 持有 last_content/last_change 锁时 blocking_send；队列容量 16。主服务处理远端剪贴板时同步调用 update_last_content，获取相同锁。
- 影响：队列满时 worker 等消费者；若消费者先处理远端更新并等待该锁，就形成循环等待。属于条件成立即可触发的锁顺序缺陷，尚未运行调度复现。
- 建议：更新缓存后在发送前释放所有同步锁；剪贴板用最新值覆盖队列更符合交互需求。
- 验收：填满队列并并发注入远端更新，在超时保护下所有任务继续推进。

### R11 / P2：接收剪贴板的 await 占住主服务事件分发

- [ ] 优化并验证。
- 证据：`src/service.rs:441` 在 handle_emulation_event 内等待 clipboard.set；虽然内部 spawn_blocking，调用者仍等待完成。
- 影响：系统剪贴板被占用/写入缓慢时，主服务无法及时处理其余事件，包括返回通知。独立输入任务不一定全部停顿，不能据此声称所有运动都被阻塞。
- 建议：有序 worker 异步执行，主循环处理完成事件；设置明确的等待/失败策略。
- 验收：假的 clipboard.set 阻塞 2 秒，主服务仍及时处理 CaptureBegin、退出和状态请求。

### R12 / P2：每个输入事件无条件格式化日志字符串

- [ ] 优化并测量。
- 证据：`src/connect.rs:158` format 在 trace 宏外执行，关闭 trace 仍格式化/分配。
- 影响：高回报率鼠标的每个事件增加不必要工作；尚无数据证明它是当前卡顿主因。
- 建议：将格式化放入惰性的日志宏，或先检查 trace 是否启用。
- 验收：关闭 trace 时热路径不因日志分配；以 1000/8000 事件每秒比较 CPU、分配次数与延迟。

## 第五轮：IPC 与后台任务生命周期

### R16 / P1：界面通知没有处理短写，可能破坏 JSON 消息边界

- [ ] 修复并验证。
- 证据：`lan-mouse-ipc/src/listen.rs:103` 对 JSON 行调用一次 write，只检查 is_err，未检查返回字节数；请求方向的 connect_async.rs 正确使用 write_all。
- 影响：大消息/发送缓冲区压力下，如果只写出部分 JSON，下一条通知会接在残缺 JSON 后面。接收器解析失败，GTK 读线程退出，进一步触发界面进程退出（见 R19）。
- 建议：完整写入每条帧，并与 R17 一起设计每客户端有界发送队列和超时。
- 验收：假 writer 每次仅接受 1–7 字节，连续多个通知均可完整解析；断开中途失败不会污染下一客户端。

### R17 / P1：慢界面客户端可阻塞整个主服务事件分发

- [ ] 修复并验证。
- 证据：`lan-mouse-ipc/src/listen.rs:94` broadcast 串行 await 每个客户端 write，无超时；`src/service.rs:199,369` 主循环 await 整个广播过程。
- 影响：一个连接仍开着却停止读取的 IPC 客户端，缓冲区满后可使主服务等待，拖延 CaptureBegin/返回通知、配置和关闭处理。输入专用任务未必全部停顿。
- 建议：独立客户端发送 worker、有界缓冲、慢消费者断开策略；状态快照可以合并，控制结果不能静默丢弃。
- 验收：一个 IPC 客户端只连接不读，另一客户端正常读取；发送足量通知后，正常客户端、返回操作和退出仍及时响应。

### R18 / P1：设备 ID 复用及旧连接回调没有代际校验

- [ ] 修复并验证。
- 证据：`src/client.rs:52,142` 使用 Slab 插入/删除可复用 handle；`src/service.rs:745` 删除设备没有取消连接/DNS任务；`src/connect.rs:269` 握手完成直接按旧 handle 更新状态，`src/service.rs:575` DNS 结果也没有比对当前 hostname/请求代次。
- 影响：删除 A 后新建 B 并复用 handle，A 的延迟握手/DNS/Pong 可写入 B 的状态。另一个相关竞态：`src/connect.rs:405` 旧 receive_loop 无条件按地址 remove，可能移除同地址的新会话。
- 建议：客户端 generation 与 connection/session ID 分开校验；删除/修改目标时取消关联任务；清理必须确认当前表项仍指向该会话。
- 验收：延迟 A 的 DNS/握手，删除 A 新建 B，再完成 A；B 不得收到 A 的地址/状态。旧会话迟到的断开也不能清理新会话。

## 第六轮：界面失败恢复与配置交互

### R19 / P2：服务断开或一条 IPC 解析错误会使界面直接退出

- [ ] 改善并验证。
- 证据：`lan-mouse-gtk/src/lib.rs:313–323` 读线程遇错误 break；`:429` 通道关闭时 process::exit(1)。没有这一条路径上的重连/断线状态界面。
- 影响：后台重启、短暂异常或 R16 的损坏帧，会表现为窗口/托盘突然消失，用户无法区分服务断线与应用崩溃。
- 建议：保留窗口并标记断线，禁用暂不可用操作，带退避重连并请求完整状态；明确显示不可恢复的协议错误。
- 验收：停止再恢复测试服务，GUI 保持可见并自动重新同步；损坏消息有可读提示，不继续展示陈旧连接成功状态。

### R20 / P2：每输入一个主机名字母就解析 DNS 并同步落盘

- [ ] 优化并验证。
- 证据：`lan-mouse-gtk/src/client_row/imp.rs:70` connect_changed 立即发 UpdateHostname；`src/service.rs:261` 更新后 save_config；`src/config.rs:786` 同步 sync_all。update_hostname 还会启动 DNS 并清空 active_addr。
- 影响：编辑过程产生不完整主机名解析、同步磁盘写入及连接状态变化；慢磁盘上的 fsync 直接延迟服务线程。不是只在点击保存后触发。
- 建议：Enter/失焦提交或适度 debounce；显示尚未应用的输入，后台原子持久化；明确无效端口输入反馈。
- 验收：输入 30 字符主机名仅提交一次最终值，中间输入不触发重连；模拟慢磁盘时返回操作仍响应。

### R21 / P2：慢的进入/离开 hook 可无限并发积累

- [ ] 改善并验证。
- 证据：`src/service.rs:896` 每次事件 spawn 独立任务和 shell 子进程，wait 无超时、并发限制或会话失效取消。
- 影响：用户配置的 hook 如果耗时或卡住，频繁穿越边缘会累积进程；旧 enter hook 可能晚于新 leave hook 完成，外部设备状态颠倒。仅配置 hook 的用户受影响。
- 建议：定义按客户端的顺序/替代策略，支持超时和退出清理，避免静默改变既有脚本的顺序语义。
- 验收：配置耗时 hook 并快速往返 100 次，进程数受控，退出能清理，最终外部状态对应最后一次边缘动作。

## 第七轮：键盘重复与失败清理

### R22 / P2：Windows 释放其他键也会停止当前键的连发

- [ ] 修复并验证。
- 证据：`input-emulation/src/windows.rs:112` 任意 key-up 均 kill_repeat_task，没有记录并核对 repeating_key；任何非锁定键的 key-down 都重启连发任务。
- 影响：按住 A，再按住 B，松开 A 时 B 的连发也停止；按住普通键时操作 Shift 等修饰键也会干扰连发。这是代码行为，尚未在 Windows 真机回归。
- 建议：跟踪实际可连发键，只有该键释放才停止；修饰键不替换连发目标；明确多普通键的策略。
- 验收：A↓、B↓、A↑ 后 B 继续重复；B↑ 后停止。按住字母切换 Shift 时不生成修饰键连发任务。

### R23 / P2：上层提前删除 emulation 映射，使失败清理无法按地址重试

- [ ] 修复并验证。
- 证据：`src/emulation.rs:493` ProxyRequest::Remove 先 self.handles.remove(addr)，再调用 emulation.destroy(handle)。`input-emulation/src/lib.rs:323` destroy 丢弃 destroy_bounded 的 false 结果，而失败时底层保留 handle 用于重试。
- 影响：上层已不认识残留 handle；同地址再次 Remove 无法重试，下一次 Input 会分配新 handle。失败释放的旧按键可能持续到整个 backend terminate 才再次清理。
- 建议：成功清理后再删除映射，或维护显式 pending-cleanup 集合并有限重试；别把输入恢复与未完成释放混为同一个新会话。
- 验收：后端首次释放超时、第二次成功；再次按地址 Remove 能清完旧 handle，不累积新旧状态。
